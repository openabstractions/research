*** CORRECTION: LEMONADE IS A C++ PROJECT NOW ***
  research/tools/lemonade.txt describes it as Python (Apache 2.0). The licence
  is right; the language is not, and the brief inherited the error. At HEAD the
  server, CLI, model manager and every backend are C++ under src/cpp/. The only
  Python file remaining anywhere under src/ is
  src/cpp/installer/generate_tauri_fragment.py, a build-time helper. The desktop
  app is Tauri (Rust shell + web front end) under src/app/.
  CONSEQUENCE FOR THE PLAN: a Lemonade fork of the downloader is C++ work, and
  our facade cannot be a Python package if it is to be linked in-process here.
  Either the facade exposes a C ABI / is itself C++, or Lemonade integrates
  across a process boundary. This is the biggest single planning surprise in the
  survey after the ComfyUI licence question.
  UNCERTAIN: when the migration happened and whether a legacy Python package is
  still published on PyPI for older installs. Not investigated.

WHAT IT USES TO TRANSFER
  libcurl (`curl_easy_*` / CURLOPT_*), wrapped by its own HttpClient. Not
  huggingface_hub, not the HF Python client, not aria2, not a vendored copy of
  anything.

  DownloadOptions defaults, verbatim from http_client.h:
    max_retries              = 5
    initial_retry_delay_ms   = 1000     (doubles each attempt)
    max_retry_delay_ms       = 60000
    resume_partial           = true     <- ON BY DEFAULT
    low_speed_limit / _time  = 0        (deliberately disabled)
    connect_timeout          = 30
    no_progress_timeout      = 60       (seconds without a byte before abort)
    range_retry_on_zero_byte_retry = true
    force_initial_range_request    = false
    expected_hash / expected_hash_algorithm
  The hash field accepts plain hex or `sha256:<hex>`, `sha1:<hex>`, or
  `git-sha1:<hex>`, and the header documents WHY: git-sha1 is
  SHA1("blob <size>\0" + bytes), which is what Hugging Face returns as the ETag
  for non-LFS files, while SHA256 covers LFS objects and release assets. That is
  a correct and non-obvious piece of Hub protocol knowledge, implemented rather
  than hand-waved.

  HUGGINGFACE_HUB v1.0 REGRESSION EXPOSURE: NONE, BY CONSTRUCTION — AND THIS IS
  THE INTERESTING PART. Lemonade talks the Hugging Face HTTP API and writes the
  Hugging Face cache layout, but it does NOT use the huggingface_hub client. So
  the v1.0 removal of `resume_download` and the dropping of hf_transfer cannot
  regress it. It independently reimplemented resume and kept it. Per
  research/transfer/SUMMARY.txt [4], huggingface_hub #4196 (2026-05-06) shows a
  16.9 GB Hub download restarting from ~404 MB after a system suspend; Lemonade
  is not subject to that failure because it never calls the regressed code.
  Of the three targets, Lemonade is the one that ALREADY SOLVED the problem this
  project exists to solve. That is the central finding of this file.


WHAT HAPPENS ON SLEEP / PROCESS DEATH
  SURVIVES, and it is the only one of the three that survives a HARD KILL
  without throwing away a large block of progress.

  - Bytes land in `<output>.partial` (http_client.cpp L1055) and are appended to
    in "ab" mode (L785). The resume offset is simply the size of that file on
    disk (L1121) — a filesystem fact, not a checkpoint that can go stale. There
    is no sidecar to lose and no part-granularity cliff: kill the process at any
    instant and you lose at most the OS write buffer.
  - Resume is a real HTTP range resume via CURLOPT_RESUME_FROM_LARGE (L815),
    with 416 handled explicitly for the "local already >= remote" case
    (L966-L1012).
  - Sleep / stall: no_progress_timeout = 60s aborts a dead connection, then the
    retry loop backs off exponentially (1s -> 60s cap, 5 attempts) and resumes
    from the .partial offset.
  - Commit is atomic: verify hash if one was supplied, THEN
    `fs::rename(.partial -> final)` (L1204-L1206), with a copy+delete fallback if
    rename fails across devices. A truncated file can never appear at the final
    name. This is exactly what ComfyUI-Manager lacks.
  - On hash mismatch the .partial is deleted, resume_offset reset to 0, and the
    file re-downloaded from scratch (L1181-L1200). Correct, if bandwidth-costly.
  - disk_full is detected and short-circuits the retry loop immediately rather
    than burning bandwidth (L1176-L1180). download_from_manifest also does a disk
    space PRE-check that credits existing .partial bytes.
  - Cancellation is cooperative and immediate via the ProgressCallback return
    value; `cancelled` is distinguished from `error` in DownloadResult.

  THE REMAINING WEAKNESS IS NOT THE BYTES, IT IS THE SNAPSHOT. An interrupted
  multi-file model leaves a half-populated `snapshots/<sha>/` directory, and the
  bugs upstream actually had were all about whether that directory is mistaken
  for a completed model. Their fix is a marker file, `.download_manifest.json`,
  written into the in-progress snapshot:
    src/cpp/server/model_manager.cpp        L693, L2196, L4969
    src/cpp/server/backends/llamacpp/llamacpp_gguf.cpp  L54
    src/cpp/server/backends/backend_ops.cpp L105-L108 — "A snapshots directory
      without a usable refs/main is an interrupted or ..." (incomplete state)
  Presence of the marker => the snapshot is in flight and must not be served.

WHERE MODELS GO, AND HOW THEY ARE NAMED
  THE HUGGING FACE HUB CACHE LAYOUT, reimplemented in C++.
    <hf_cache>/models--<org>--<repo>/
        refs/main                       -> commit sha
        snapshots/<commit-sha>/<files>
        blobs/<sha256>                  (see the caveat below)
        snapshots/<sha>/.download_manifest.json   while in flight
    Naming: src/cpp/server/model_registry.cpp
      registry_repo_cache_dir_name(repo_id, source)   L961-L970
        prefix "models--" for Hugging Face,
               "modelscope--models--" for ModelScope,
        then repo_id with every '/' replaced by '--'.
      ModelScope is a first-class second registry sharing the same root under a
      separate namespace (docs/embeddable/models.md L75).

    *** THE CAVEAT THAT MATTERS FOR A SHARED STORE ***
    Lemonade READS the HF blobs+symlinks layout but does NOT WRITE it. Verbatim
    from src/cpp/server/model_manager.cpp L435-L443:
      "HF hub downloads use: snapshots/<hash>/file.gguf -> ../../blobs/<sha256>
       ... This would need integration tests that use huggingface_hub Python
       tooling (e.g. hf_hub_download()) to create the blob+symlink layout, since
       Lemonade's own downloader writes real files without blobs."
    So a cache populated BY Lemonade contains real files inside snapshots/, while
    a cache populated by huggingface_hub contains symlinks into blobs/. Both are
    readable by Lemonade (cleanup_orphaned_blob at L445 handles the symlink case
    and garbage-collects unreferenced blobs). The layouts are READ-COMPATIBLE but
    NOT WRITE-IDENTICAL. Any shared store we build has to tolerate both shapes in
    the same tree, and cannot assume blobs/ is authoritative. This is a concrete,
    citable requirement for the store abstraction.

  Consequence for cross-tool dedup: Lemonade's identity key is
  (registry, repo_id, commit-sha, filename). Ollama's is a sha256 over an OCI
  layer. ComfyUI's is (folder key, filename). Only Lemonade's maps cleanly onto
  an upstream, publicly resolvable identity — which makes it the best candidate
  to be the CANONICAL layout for a shared store.

    behaviour a shared store wants from a participant.

HOW PLUGGABLE IS IT?
  EASIEST OF THE THREE, and it already has TWO layered seams.

  SEAM 1 — the backend virtual (per-backend override, already exercised):
    src/cpp/include/lemon/backends/backend_ops.h
      class BackendOps                                          L41
        virtual void download_model(const ModelInfo&, bool do_not_upgrade, ...)  L104
        virtual bool invalidates_cache_after_download() const    L110
        virtual bool is_downloaded(const ModelInfo&, const BackendOpsContext&)   L94
    The default implementation delegates to
    ModelManager::download_from_registry_engine (model_manager.h L303-L306), and
    the flm and cloud backends ALREADY override it with their own download. So
    "a different downloader per backend" is not a hypothetical — it is a shipped,
    used extension point. There is also
    backend_self_manages_downloads(recipe) (model_manager.h L297) for backends
    that fetch their own weights.

  SEAM 2 — the transport (single choke point):
    HttpClient::download_file has exactly six call sites (listed above), all in
    C++ we control, all taking the same DownloadOptions/ProgressCallback pair.
    Replacing the body of that one static function routes EVERY download in the
    product — models, backend binaries, whisper weights, recipe imports —
    through our facade. That is a one-function change.

  The existing DownloadOptions/DownloadResult/ProgressCallback triple is, frankly,
  close to the interface our facade should expose. It already models: resume,
  cancellation, expected hash with algorithm prefixes, disk-full, permanent vs
  retryable failure, and a security policy for redirect targets. WE SHOULD STEAL
  THIS SHAPE rather than invent one. Per the project's own rule — prefer adopt or
  wrap over build — the honest reading is that Lemonade has already written a
  large part of the abstraction we were going to write.

  Estimated change size: a handful of call sites; one function body if we take
  Seam 2. Not pervasive.


FORK FRICTION
  Activity: 481 commits to main between 2026-05-20 and 2026-08-19 (~5.3/day) —
  nearly ComfyUI-level churn, far above Ollama, and vendor-funded so it is
  unlikely to slow. HEAD moved the day before this survey.
  Rebase risk: MODERATE-TO-HIGH by commit rate, but MITIGATED by structure: the
  code we would touch (http_client.cpp, backend_ops.h) is infrastructure that
  most of that churn does not go near — the churn is in backends, router,
  server endpoints and the Tauri app. A one-function replacement behind an
  existing virtual is about as rebase-proof as a fork gets.
  Build friction is the real cost, not merge friction: CMake + C++ + libcurl +
  a Tauri/Rust desktop shell + multiple vendored inference backends. Anyone
  forking this needs a working native toolchain on Windows, which is a heavier
  lift than `go build` or editing a .py file.
  Apache-2.0 means no licence obligation on the fork, and it is the friendliest
  licence of the three for CONTRIBUTING BACK — which, given that they have
  already solved resume properly, may be more valuable than forking.
