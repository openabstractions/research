WHAT IT USES TO TRANSFER
  Go standard library `net/http` in both paths. No third-party downloader, no
  huggingface_hub, no aria2, no libcurl.
    - Path A: `http.DefaultClient.Do(req)` HARDCODED at download.go L345. There
      is no injectable client on this path at all. Auth/manifest/redirect calls
      go through makeRequestWithRetry, but the bulk body transfer does not.
    - Path B: `opts.Client` if set, else a package-level pooled client
      (transfer.go L68/L122). This IS an injection point, and it is the only one
      in the tree.
  Parallelism: Path A issues up to 16 concurrent ranged GETs
  (`Range: bytes=<start>-<stop-1>`, download.go L344) against a redirect-resolved
  direct CDN URL, writing into one sparse file via io.NewOffsetWriter.
  Path B does whole-blob GETs, N blobs in parallel, bounded by
  BodyConcurrency (envconfig MaxTransferStreams).

  NOT AFFECTED by the huggingface_hub v1.0 regression (removal of
  `resume_download`, dropping of hf_transfer). Ollama has no Python in the
  download path and no dependency on the Hub client. Ollama is the only one of
  the three targets that is immune here.


WHAT HAPPENS ON SLEEP / PROCESS DEATH
  Three distinct behaviours; the docs and the bug reports genuinely conflict,
  and the code explains why both are right.

  1. LAPTOP SLEEP / NETWORK STALL — survives, cleanly. Path A runs a watchdog
     goroutine per chunk (download.go L368-L393). If no byte arrives for 30s it
     returns errPartStalled, which cancels only that chunk's sub-context. The
     retry loop at L287-L305 treats a stall specially: `try--` (L292), so stalls
     do NOT consume the 6-retry budget — it retries forever. The retry re-issues
     `Range: bytes=<Offset+Completed>-` so it picks up where it left off.
     Practically: close the lid, come back, the pull continues.
     UNVERIFIED by us on real hardware; this is a code reading.

  2. CTRL-C / GRACEFUL SHUTDOWN — resumes correctly. Context cancellation makes
     io.CopyN return, and the code still runs `part.Completed.Add(n)` and
     `writePart(...)` (download.go L358-L364) before propagating. The JSON
     sidecar is up to date, and the next `ollama pull` resumes.

  3. HARD KILL / POWER LOSS / VM HANG — loses a LOT, and this is the mechanism
     behind every "it restarted from zero" report. The checkpoint sidecar is
     written ONLY when a chunk attempt ends. Each part is transferred by a single
     io.CopyN covering the whole remaining part (L354), so between the start and
     the end of a part there is no checkpoint at all. Checkpoint granularity is
     therefore ONE PART = 100 MB to 1000 MB. With 16 parts in flight, a SIGKILL
     discards the uncommitted progress of all 16 simultaneously. On a 4 GB model
     (250 MB parts) that is up to 4 GB of progress thrown away — indistinguishable
     from "restarted from zero" to the user filing the bug.

  CORRUPTION: `run()` truncates the partial file to full size up front and marks
  it sparse (L222-L232, plus server/sparse_windows.go / sparse_common.go). A
  crash therefore leaves a FULL-SIZE file containing holes. That is exactly the
  state described in #17520. Worse, a blob that already exists on disk is never
  re-verified: downloadBlob returns cacheHit=true on a bare os.Stat (download.go
  L487-L500), and PullModel skips verifyBlob for cache hits (images.go
  L1044-L1062, `skipVerify`). `ollama pull` then PRINTS "verifying sha256 digest"
  and "success" while verifying nothing. Confirmed by code and by the reporter.
  The maintainer claim that "restart does a housekeeping sweep" (cited in #17520
  from #16801) is not supported by the code: server/fixblobs.go only renames
  `sha256:` to `sha256-`. It never hashes anything. DOCS/MAINTAINER CLAIM
  CONFLICTS WITH CODE; the code and the user report agree against the claim.

WHERE MODELS GO, AND HOW THEY ARE NAMED
  Content-addressed blobs + OCI-style manifests. Implementation is now in the
  `manifest` package (it moved out of the old server/modelpath.go):
    manifest/paths.go
      Path()                -> $MODELS/manifests
      PathForName(n)        -> $MODELS/manifests/<host>/<namespace>/<model>/<tag>
      BlobsPath(digest)     -> $MODELS/blobs/sha256-<64 hex>
                               (":" is rewritten to "-" for Windows path safety;
                               a strict `^sha256[:-][0-9a-fA-F]{64}$` regex gates it)
      PruneDirectory(path)  -> removes empty dirs
    In-flight files sit beside the final blob:
      $MODELS/blobs/sha256-<hex>-partial      the sparse data file
      $MODELS/blobs/sha256-<hex>-partial-<N>  one JSON checkpoint per part
    server/fixblobs.go  renames legacy `sha256:` names to `sha256-`. Nothing else.

  Consequences for a shared store: the blob namespace is a FLAT directory of
  sha256-named files. That is the friendliest of the three layouts to dedupe
  against — but the digest is over the Ollama layer, not over the GGUF file as
  Hugging Face would hash it, so blobs are NOT interchangeable with an HF cache
  without a translation table.


EXTERNAL MODEL DIRECTORY TODAY
  YES, config alone, and it is the cleanest of the three.
    envconfig/config.go
      Models() L111-L123 — `OLLAMA_MODELS`, else $HOME/.ollama/models
      registered in the env table at L329
  Everything (manifests + blobs + partials) moves as one tree. Limitations:
    - single root only; no multi-root search path, no read-only base + writable
      overlay, no per-type redirection.
    - the server process must be able to write it; on Linux the systemd unit runs
      as the `ollama` user, which is the usual reason OLLAMA_MODELS "doesn't work".
    - symlinking $MODELS/blobs at a shared store works mechanically (blobs are
      opaque files) but nothing upstream tests or supports it. UNVERIFIED.


HOW PLUGGABLE IS IT?
  Split verdict.

  PATH B is genuinely pluggable already: `transfer.DownloadOptions.Client` is an
  injectable `*http.Client` and the options struct also exposes Progress,
  StallTimeout, BodyConcurrency, GetToken. An http.RoundTripper swap gets you a
  long way with zero upstream edits. But this path only handles tensor layers,
  so it does not cover the GGUF pulls we care about.

  PATH A has NO seam. `http.DefaultClient` is a package-level literal at L345;
  blobDownload is an unexported struct in package `server`; there is no
  interface, no constructor injection, no functional option anywhere in the file.

  BUT the blast radius is small, which is the point:
    - ONE entry point (`downloadBlob`, download.go L476)
    - ONE call site (images.go L1044)
    - ONE progress contract to preserve (`func(api.ProgressResponse)`), which is
      already a callback and is exactly the shape a facade wants
    - ONE file to replace end to end (download.go, 517 lines)
  A fork that defines `type BlobFetcher interface { Fetch(ctx, digest, size,
  destPath, progress) error }`, keeps the existing implementation as the default,
  and swaps in ours behind an env var touches roughly: download.go (rewrite),
  images.go (2 call sites: L1044 and L1173), plus one wiring file. Estimate:
  a handful of call sites, NOT pervasive. This is the smallest downloader-fork
  surface of the three targets by a wide margin.

  Upstream has already signalled the direction: x/transfer/transfer.go L7 carries
  `TODO (jmorganca): Integrate into server/download.go and server/upload.go when
  stable.` Upstream intends to collapse the two paths into one. A fork that
  introduces the interface is moving WITH that current, and an upstreamable PR
  is plausible.
