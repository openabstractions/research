VERDICT — against the kill condition stated in advance
  research/tools/logging.txt wrote, before any data existed:
    "if every tool already writes to a predictable per-user location and total
     log volume is under a few tens of MB/day, there is no seam here and this
     file should record that and stop."

  1. VOLUME: DEAD, decisively. 2.47 MiB accumulated over roughly three days,
     against 116 GB of model weights on the same disk. The disk-wear and
     write-amplification argument is not merely unproven, it is refuted by four
     orders of magnitude. Do not make this argument again.

  2. PREDICTABLE LOCATION: MOSTLY YES, and the exception is small. LM Studio,
     Ollama and Jan each write to one predictable per-user directory. ComfyUI is
     genuinely scattered — 4 names across 2 directories — and HuggingFace grows a
     new file per process forever. So the "can the user find them?" number is
     SEVEN directories across FOUR root trees. That is annoying. It is not
     system-degrading.

  3. THEREFORE: on these numbers, log placement/budget/retention does NOT justify
     building a logging service on its own. Recorded, and stopped, as the file
     said to.

WHAT SURVIVES, AND IT IS A DIFFERENT ARGUMENT
  Logging should not be pitched as its own product on this evidence. What it can
  be is a CONSUMER of the job/service substrate: once a system service exists
  with discovery and delegation (see research/transfer/SUMMARY.txt and
  research/async/), an app logging to it instead of to a private file costs
  almost nothing to add and gives one enumerable sink for free. That is a
  near-zero-cost feature of an abstraction justified elsewhere — not a
  justification for building one.

  The two findings above that are worth carrying forward:
   - HuggingFace xet writes an unrotated log per process and accounts for 70% of
     all log bytes here. If any single thing gets fixed, it is that one, and it
     is in the same subsystem already implicated in the resume failures.
   - ComfyUI's four ad-hoc log files are a symptom of the same thing that makes
     it identify models by filename: nothing in it has an owner. Relevant to the
     fork, not to a logging product.
