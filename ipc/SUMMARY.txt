LOCAL IPC / CHANNEL SURVEY — SUMMARY
====================================

SCOPE: prior art for a channel layer whose two ends know each other, established
once (SCOPE.md §5, item 3). The question it was run to settle: is the layer
IDENTITY-THEN-POLICY ("who is calling, and may they") or CAPABILITY-BASED ("the
reference you hold is your permission")? Those choose different wire formats, so
it cannot be deferred.
ADDED: 2026-09-05. Facts sourced in the individual profiles.

THE FINDING
  1. THE NATIVES ALREADY DO MOST OF IT. Windows, macOS and Linux each provide a
     local channel AND an authoritative principal for its peer. A facade over
     the three is thin. Its entire difficulty is presenting three different
     STRENGTHS of answer without lying about any — see caller-identity.txt.
     This argues for facing the natives, not adopting a framework that
     abstracts the transport and hides the property we need.

  2. THE QUESTION MAY BE THE WRONG ONE. Everything except Cap'n Proto helps a
     service ask "who is calling". Cap'n Proto removes the question: holding the
     reference IS the permission.
     And the industry has already drifted there without naming it. Wayland and
     D-Bus, having found peer interrogation unportable, now hand each
     application instance its own socket with metadata attached at creation.
     That construction is a capability.
     If we follow it deliberately, most of a rights-and-ownership layer does not
     need to be built. That is a better outcome than building it well.

  3. WHAT SURVIVES UNDER EITHER MODEL IS BOOTSTRAP. Somebody still decides which
     capability an application is handed the FIRST time. Platform identity
     re-enters exactly there, once, at channel creation — which is also where
     SCOPE.md concluded identity should be bound. The two answers agree.

RECOMMENDATION
  Design the channel as capability-passing over the platform-native transports,
  with platform identity used ONLY at bootstrap. Do not adopt D-Bus (licence) or
  gRPC (wrong half). Cap'n Proto is the closest existing thing and is worth
  prototyping against; varlink is the fallback if its multi-language RPC story
  proves too thin, since a small JSON protocol is something this project has
  already shown it can implement three times and conformance-test.

  NOT A DECISION TO TAKE YET. SCOPE.md §4: no new layer starts until an existing
  layer has an adopter who is not us. This survey exists so that when that
  happens, the shape is already argued rather than improvised.

THE MOTIVATING SCENARIO, WHICH IS ALSO THE HARDEST TEST
  Installers ask for admin and then may do anything. That is ambient authority:
  the program acts with all the power of whoever ran it, scoped to nothing. It
  is the exact condition capability security was invented against, and it is the
  strongest argument in this file for the capability model.

  Note the asymmetry, because it says where the gap is. The industry fixed
  RUNTIME permissions — iOS 4 prompts (2010), iOS 6's Privacy pane (2012),
  Android 6.0 runtime permissions (2015), macOS TCC, polkit actions — and left
  INSTALL-TIME elevation alone. All of those predate GDPR (2018) by years; they
  came from vendors under pressure, not from regulation, which means the change
  is reachable without one.
  The reason install-time lagged is real and not laziness: "may use your camera"
  is evaluable by a person and "may write under /usr/lib" is not. Runtime
  permissions attach to scenarios; install actions attach to paths.
  The partial answer that exists is to make installation DECLARATIVE rather than
  executable — MSIX declared capabilities, Flatpak's permission manifest, polkit
  per-action policy, .deb/.rpm letting the manager rather than the package do
  the writing. Four platforms, four vocabularies, no common answer. The same
  fragmentation as caller-identity.txt found, one level up.

  WHAT THIS DEMANDS OF US, and it is where capabilities are weakest:
  - REVOCATION. "Grant a few, change your mind later" is the whole point of the
    scenario. Capabilities are excellent at unforgeable grant and historically
    poor at withdrawal; this needs an answer, not a hope.
  - LEGIBILITY. A person must be able to see what an application currently
    holds. An unforgeable reference nobody can enumerate is not auditable.
  - NO BLANKET ESCAPE HATCH BY DEFAULT. Vista's UAC is the case study: the
    escape hatch did not absorb the impatient, it became the default path and
    people disabled UAC entirely. Design constraint that follows: the granular
    path must be EASIER than the blanket one, not merely available. If three
    specific grants cost more clicks than one total grant, the granular model is
    decorative.

OPEN, AND WORTH RESOLVING BEFORE ANY CODE
  - Cap'n Proto on Windows with MSVC: current state UNVERIFIED.
  - varlink on Windows and macOS: implementations UNVERIFIED.
  - sd-bus and sd-varlink licences: assumed LGPL-2.1, UNVERIFIED.
  - Revocation and enumeration under a capability model — see above. This is now
    a requirement from the motivating scenario, not a caveat, and it is the one
    thing that could sink the recommendation.
